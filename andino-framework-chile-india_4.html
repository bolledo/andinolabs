Handoff comercial → operaciones

El momento más crítico: cuando el cliente dice "sí". Este handoff define la calidad del kick-off.

📋 Sale Package — entrega comercial
  • Propuesta firmada con scope, precio y condiciones
  • Notas del discovery comercial — dolores y motivaciones
  • Stakeholders del cliente: quién decide, usa, paga
  • Compromisos de timeline dados durante la venta
  • Riesgos identificados en el proceso comercial
  • Contexto cultural del cliente (tamaño, industria, sensibilidades)
🚀 Project Package — recibe el Project Lead
  • Briefing de 30 min con CEO o Country Manager USA
  • Acceso al CRM con todas las notas del deal
  • Intro al cliente hecha por el vendedor (email + llamada)
  • Asignación del equipo India con Chief AI & Delivery
  • Fecha de kick-off acordada con el cliente
  • Repo creado, canales Teams configurados, accesos listos
⚠️ Regla del handoff: El Project Lead no contacta al cliente hasta que el briefing con el vendedor esté completo y la intro haya sido hecha. Un Project Lead sin contexto genera una primera impresión débil que el equipo paga durante semanas.

¿Cómo funciona Andino a nivel de proyecto?

Squads pequeños y enfocados. Chile lidera — cliente, scope y decisiones. India ejecuta el delivery técnico. El framework estandariza cómo se conectan ambos lados.

Modelo de colaboración: Chile es el punto de contacto con el cliente — entiende el negocio, prioriza el scope, valida el output. India traduce ese scope en software con autonomía técnica. La coordinación es complementaria, no jerárquica: cada lado tiene un dominio de ownership claro.

Principios del framework

🎯 Claridad ante todo
  • Cada ticket tiene un owner único
  • Intent documentado antes de codificar
  • Sin trabajo sin contexto escrito
  • Decisiones registradas en Jira/Confluence
⚡ Velocidad asimétrica
  • India opera ~10h de adelanto a Chile
  • Rituales anclados en overlap horario
  • Trabajo asíncrono como default
  • Bloqueos escalados en <2h
🤖 AI-native por defecto
  • Nébula + Claude Code en cada proyecto
  • Context Engine actualizado por sprint
  • Prompts y workflows documentados
  • Métricas de adopción de IA por proyecto

Protocolo asíncrono

  • Deja contexto en PRs abiertos
  • Prepara preguntas en el canal de Teams del proyecto

🌅 Al empezar tu turno
  • Lee el stand-up escrito del otro equipo
  • Revisa Jira: tickets y comentarios nuevos

  • Decisiones de arquitectura
  • Cambios de scope → llamada primero
  • Bloqueos críticos → escalar inmediato
  • Kick-off de Bolt → siempre en vivo

⚠️ Regla de oro: Si estás bloqueado más de 2 horas, escalas. No esperes el stand-up del día siguiente.

Onboarding al proyecto

Cuando llega un nuevo integrante, este proceso asegura que esté operativo en menos de 1 día hábil.

🇨🇱 Chile — Project Lead
1
Briefing con comercial (30 min)
CEO o Country Manager USA hace el traspaso: negocio del cliente, historia del deal, stakeholders y compromisos dados durante la venta.
2
Leer el Project Brief en Confluence
Stack, decisiones de arquitectura, Bolts anteriores, feedback del cliente y métricas actuales.
3
Meet con India Tech Lead (30 min)
Presentación, expectativas de trabajo, timezone, preferencias de comunicación y acuerdos de disponibilidad.
4
Accesos y canales
Jira, Team en Teams, Confluence. Intro al cliente hecha por el vendedor antes del primer contacto directo.
🇮🇳 India — Dev / Tech Lead
1
Setup técnico (2h máx)
Repo clonado, dependencias instaladas, env local funcionando, Nébula + Claude Code configurado. Sin esto, no hay día 1 productivo.
2
Leer el Context Engine del proyecto
Arquitectura, ADRs, convenciones de código y guías de contribución en Confluence.
3
Primer good-first-issue
Chile prepara un ticket etiquetado para el día 1. Objetivo: un PR chico para conocer el proceso completo.
4
Meet con Chile Lead (30 min)
Expectativas, acuerdos de comunicación, repaso del Bolt actual. Preguntas sin filtro bienvenidas.

Métricas del framework

Métricas en dos niveles: empresa (portfolio, revenue) y proyecto (delivery, colaboración, IA). Revisadas en sus respectivas ceremonias.

🏛️ Métricas de empresa — Portfolio Review mensual

💼 Revenue & pipeline
  • Pipeline value — total deals activos LATAM + USA
  • Win rate — % propuestas que cierran (target ≥40%)
  • Sales cycle — días primer contacto → firma (target ≤21d)
  • Revenue por proyecto — vs. costo operacional Chile+India
📊 Portfolio health
  • Proyectos on-track — % sin riesgo de delivery (target ≥85%)
  • NPS del cliente — encuesta post-Bolt, score agregado
  • Utilización India — % capacidad asignada a proyectos activos
  • Churn — contratos no renovados o cancelados

🔧 Métricas de proyecto — Retro quincenal

📊 Delivery
  • Bolt completion rate — % Units entregadas (target ≥85%)
  • Cycle time — ticket creado → Done (target <5 días)
  • PR review time — PR abierto → aprobado (target <4h)
  • Defect escape rate — bugs post-demo (target 0)
🤖 Adopción IA
  • AI usage rate — % tickets con Nébula/Claude Code (target ≥80%)
  • Context Engine freshness — % docs actualizados en el último Bolt
  • Prompt reuse rate — % prompts del canal #ai-prompts reutilizados

Descriptores de cargo — Andino Labs

Descripción detallada de cada rol: propósito, responsabilidades por dominio, límites de autoridad y criterios de éxito. Estos descriptores son el contrato interno de cada persona con la organización.

🤖
Chief AI & Delivery
Rol único en Andino · Reporta al CEO · Transversal a todos los proyectos y al C-Level
El Chief AI & Delivery no gestiona un proyecto — gestiona el sistema que hace que todos los proyectos funcionen. Su trabajo es asegurarse de que los Project Leads tienen lo que necesitan, que India está ejecutando con calidad, que la IA se está usando de verdad y que el framework se mejora con cada ciclo. Cuando algo falla en un proyecto, es la primera persona que lo sabe después del Project Lead y la que decide si hay que escalar o resolver.
Responsabilidades por dominio

Lo que el rol NO es

🚫 NO hace esto
  • Gestionar el día a día de un proyecto — eso es el Project Lead
  • Revisar tickets o hacer code review — eso es el India TL
  • Hablar directamente con el cliente sin pasar por Chile Lead
  • Tomar decisiones de scope — eso es el Project Lead con el cliente
  • Resolver dudas técnicas de implementación — eso es el India TL
  • Micro-gestionar cómo India usa Nébula en cada línea de código
  • Escalar al CEO sin haber intentado resolver el problema primero
✅ SÍ hace esto
  • Detectar patrones de riesgo antes de que el Project Lead los vea
  • Intervenir en proyectos con señales de deterioro — proactivamente
  • Asegurar que el framework evoluciona con cada ciclo de aprendizaje
  • Ser el puente entre lo técnico (India) y lo estratégico (C-Level)
  • Empujar la adopción de IA sin generar ruido operacional
  • Defender la calidad del delivery cuando hay presión comercial
  • Decirle "no" al CEO si un compromiso de timeline es irrealizable
🇨🇱
Project Lead — Chile
Owner del proyecto · Reporta al Chief AI & Delivery · Interfaz única con el cliente
El Project Lead es la cara de Andino ante el cliente y el director de orquesta del proyecto. Entiende el negocio del cliente mejor que nadie en el equipo, traduce ese contexto en un backlog priorizado y se asegura de que India tiene todo lo que necesita para ejecutar. No codifica — lidera. Su autoridad es sobre el qué y el cuándo; la autoridad técnica sobre el cómo es del India Tech Lead.
🚫 NO hace esto
  • Comprometer timelines sin validar capacidad con India primero
  • Abrir tickets sin acceptance criteria escritos y claros
  • Saltarse al India TL para hablar directamente con los devs
  • Comenzar a codificar antes de tener el Intent Document validado
  • Ocultar riesgos al Chief AI & Delivery para "resolverlos solo"
  • Modificar el scope acordado sin registrarlo en Jira y notificar a India
✅ SÍ hace esto
  • Escribe el Intent Document antes de cada kick-off de Bolt
  • Valida cada entregable contra acceptance criteria antes del demo
  • Envía el check-in semanal al Chief AI & Delivery cada viernes
  • Escala riesgos de forma proactiva — no espera a que exploten
  • Gestiona las expectativas del cliente antes de que se generen
  • Defiende el scope acordado frente a pedidos de último minuto
🇮🇳
Tech Lead — India
Owner técnico del proyecto · Reporta al Chief AI & Delivery · Interfaz principal con el Project Lead
El Tech Lead India es la cabeza técnica del equipo de ejecución. Toma todas las decisiones de arquitectura, diseña la solución a partir del Intent Document, asigna trabajo a los devs, hace el code review y es la fuente de verdad técnica del proyecto. Su autoridad es sobre el cómo; la autoridad sobre el qué y la prioridad es del Project Lead Chile. Es el único punto de contacto técnico habitual con Chile Lead — los devs no van directamente a Chile.
🚫 NO hace esto
  • Tomar decisiones de scope o prioridad sin alinear con Chile Lead
  • Ignorar un bloqueo por más de 2 horas sin escalarlo
  • Comenzar a implementar sin Intent Document validado
  • Contactar al cliente directamente sin acuerdo con Chile Lead
  • Aprobar un PR sin code review real por presión de tiempo
  • Dejar el Context Engine desactualizado al cerrar el Bolt
✅ SÍ hace esto
  • Estima con honestidad — da rangos, no promete números exactos bajo presión
  • Propone soluciones técnicas alternativas cuando el approach original no es viable
  • Actualiza el Context Engine como parte de cada PR, no como tarea aparte
  • Prepara 3 puntos de fricción técnica para la Tech Review mensual
  • Escala bloqueos técnicos rápido — el silencio no es profesionalismo
  • Hace code review que enseña, no solo que aprueba o rechaza
💻
Developer — India
Ejecutor técnico · Reporta al India Tech Lead · Opera con autonomía dentro del Intent Document
El Developer India es quien hace que las cosas sucedan. Implementa con autonomía técnica dentro del scope definido en el Intent Document, usa Nébula y Claude Code como herramientas de default (no como opción), reporta su progreso y bloqueos de forma proactiva, y contribuye a la documentación técnica del proyecto. Su canal habitual es el India Tech Lead — no va directamente a Chile Lead salvo acuerdo previo.
🚫 NO hace esto
  • Asumir silenciosamente que entiende un ticket ambiguo — pregunta primero
  • Implementar sin leer el Intent Document del Bolt
  • Ignorar un bloqueo por más de 2 horas sin escalar al TL
  • Cerrar un ticket sin tests y sin documentación técnica
  • Usar el stack o enfoque que le gusta sin consultar al TL
  • Saltar el proceso de PR por presión de tiempo
✅ SÍ hace esto
  • Usa Nébula y Claude Code en cada ticket — documenta cómo en el PR
  • Postea el stand-up asíncrono todos los días a las 09:30 IST sin excepción
  • Escribe PRs con contexto suficiente para que el TL haga un review real
  • Actualiza el Context Engine cuando cierra un ticket con decisiones técnicas relevantes
  • Pregunta en el canal del proyecto, no en DMs — el contexto beneficia a todo el equipo
  • Completa el good-first-issue el día 1 de onboarding sin esperar ayuda
