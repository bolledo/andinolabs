Sales → Operations Handoff

The most critical moment: when the client says "yes." This handoff defines kick-off quality.

📋 Sale Package — what sales delivers
  • Signed proposal with scope, price and terms
  • Sales discovery notes — pain points and motivations
  • Client stakeholders: who decides, uses, pays
  • Timeline commitments made during the sale
  • Risks identified during the sales process
  • Client context (size, industry, sensitivities)
🚀 Project Package — what the Project Lead receives
  • 30-min briefing with CEO or Country Manager USA
  • CRM access with all deal notes
  • Client intro made by the seller (email + call)
  • India team assignment con Chief AI & Delivery
  • Kick-off date agreed with the client
  • Repo created, Teams channels set up, accesses ready
⚠️ Handoff rule: The Project Lead does not contact the client until the seller briefing is complete and the intro has been made. A Project Lead without context creates a weak first impression that the team pays for over weeks.

Framework Principles

🎯 Clarity first
  • Every ticket has a single owner
  • Intent documented before coding
  • No work without written context
  • Decisions recorded in Jira/Confluence
⚡ Asymmetric speed
  • India runs ~10h ahead of Chile
  • Rituals anchored in overlap window
  • Async work as default
  • Blockers escalated in <2h
🤖 AI-native by default
  • Nébula + Claude Code on every project
  • Context Engine updated each sprint
  • Prompts and workflows documented
  • AI adoption metrics per project

Project Onboarding

When a new team member joins, this process ensures they are operational in less than 1 business day.

🇨🇱 Chile — Project Lead
1
Sales briefing (30 min)
CEO or Country Manager USA delivers the handoff: client business, deal history, stakeholders and commitments made during the sale.
2
Read the Project Brief in Confluence
Stack, architecture decisions, previous Bolts, client feedback and current metrics.
3
Meet with India Tech Lead (30 min)
Introduction, working expectations, timezone, communication preferences and availability agreements.
4
Accesses and channels
Jira, Teams channel, Confluence. Client intro made by the seller before first direct contact.
🇮🇳 India — Dev / Tech Lead
1
Technical setup (max 2h)
Repo cloned, dependencies installed, local env working, Nébula + Claude Code configured. Without this, there is no productive Day 1.
2
Read the project's Context Engine
Architecture, ADRs, code conventions and contribution guides in Confluence.
3
First good-first-issue
Chile prepares a labeled ticket for Day 1. Goal: a small PR to learn the full process end-to-end.
4
Meet with Chile Lead (30 min)
Expectations, communication agreements, current Bolt walkthrough. Unfiltered questions welcome.

Framework Metrics

Metrics at two levels: company (portfolio, revenue) and project (delivery, collaboration, AI). Reviewed at their respective ceremonies.

🏛️ Company Metrics — Monthly Portfolio Review

💼 Revenue & pipeline
  • Pipeline value — total active deals LATAM + USA
  • Win rate — % prproposals that close (target ≥40%)
  • Sales cycle — days first contact → signature (target ≤21d)
  • Revenue per project — vs. costo operacional Chile+India
📊 Portfolio Health
  • Projects on-track — % without delivery risk (target ≥85%)
  • NPS dthe client — encuesta post-Bolt, score agregado
  • India utilization — % capacity assigned to active projects
  • Churn — contracts not renewed or cancelled

🔧 Project Metrics — Bi-weekly Retro

📊 Delivery
  • Bolt completion rate — % Units delivered (target ≥85%)
  • Cycle time — ticket created → Done (target <5 days)
  • PR review time — PR opened → approved (target <4h)
  • Defect escape rate — bugs post-demo (target 0)
🤖 AI Adoption
  • AI usage rate — % tickets with Nébula/Claude Code (target ≥80%)
  • Context Engine freshness — % docs updated in the last Bolt
  • Prompt reuse rate — % prompts del canal #ai-prompts reutilizados

Job Descriptions — Andino Labs

Detailed description of each role: purpose, domain responsibilities, authority boundaries and success criteria. These job descriptions are each person's internal contract with the organization.

🤖
Chief AI & Delivery
Unique role at Andino · Reports to CEO · Transversal across all projects and C-Level
The Chief AI & Delivery does not manage a project — they manage the system that makes all projects work. Their job is to ensure Project Leads have what they need, that India is executing with quality, that AI is genuinely being used, and that the framework improves with each cycle. When something fails in a project, they are the first to know after the Project Lead, and the one who decides whether to escalate or resolve.
Responsibilities by Domain

What the Role Is NOT

🚫 Does NOT do this
  • Manage day-to-day of a project — that's the Project Lead
  • Review individual tickets or do code review — that's the India TL
  • Talk directly with the client without going through Chile Lead
  • Make scope decisions — that's the Project Lead with the client
  • Resolve technical implementation questions — that's the India TL
  • Micro-manage how India uses Nébula on every line of code
  • Escalate to CEO without having tried to solve the problem first
✅ DOES do this
  • Detect risk patterns before the Project Lead sees them
  • Intervene in projects showing deterioration signals — proactively
  • Ensure the framework evolves with each learning cycle
  • Bridge the technical (India) and the strategic (C-Level)
  • Push AI adoption without generating operational noise
  • Defend delivery quality when there is commercial pressure
  • Say "no" to the CEO when a timeline commitment is unrealistic
🇨🇱
Project Lead — Chile
Project owner · Reports to Chief AI & Delivery · Single interface with the client
The Project Lead is Andino's face to the client and the project's orchestrator. They understand the client's business better than anyone on the team, translate that context into a prioritized backlog, and ensure India has everything it needs to execute. They don't code — they lead. Their authority is over the what and the when; technical authority over the how belongs to the India Tech Lead.
🚫 Does NOT do this
  • Comprometer timelines sin validar capacidad con India primero
  • Abrir tickets sin acceptance criteria escritos y claros
  • Saltarse al India TL para hablar directamente con los devs
  • Comenzar a codificar antes de tener el Intent Document validado
  • Ocultar riesgos al Chief AI & Delivery para "resolverlos solo"
  • Modificar el scope acordado sin registrarlo en Jira y notificar a India
✅ DOES do this
  • Escribe el Intent Document antes de cada kick-off de Bolt
  • Valida cada entregable contra acceptance criteria antes del demo
  • Sends the weekly check-in to the Chief AI & Delivery every Friday
  • Escala riesgos de forma proactiva — no espera a que exploten
  • Gestiona las expectativas dthe client antes de que se generen
  • Defends the agreed scope against last-minute requests
🇮🇳
Tech Lead — India
Technical project owner · Reports to Chief AI & Delivery · Primary interface with the Project Lead
The India Tech Lead is the technical head of the execution team. They make all architecture decisions, design the solution from the Intent Document, assign work to devs, do code review, and are the technical source of truth for the project. Their authority is over the how; authority over the what and priority belongs to Chile Lead. They are the only regular technical contact point with Chile Lead — devs do not go directly to Chile.
🚫 Does NOT do this
  • Tomar decisiones de scope o prioridad sin alinear con Chile Lead
  • Ignore a blocker for more than 2 hours without escalating it
  • Comenzar a implementar sin Intent Document validado
  • Contactar to the client directamente sin acuerdo con Chile Lead
  • Approve a PR without a real code review due to time pressure
  • Dejar el Context Engine desactualizado al cerrar el Bolt
✅ DOES do this
  • Estimates honestly — gives ranges, doesn't promise exact numbers under pressure
  • Proposes alternative technical solutions when the original approach is not viable
  • Actualiza el Context Engine como parte de cada PR, no como tarea aparte
  • Prepares 3 technical friction points for the monthly Tech Review
  • Escalates technical blockers quickly — silence is not professionalism
  • Does code review that teaches, not just approves or rejects
💻
Developer — India
Technical executor · Reports to India Tech Lead · Operates autonomously within the Intent Document
The India Developer is the one who makes things happen. They implement with full technical autonomy within the scope defined in the Intent Document, use Nébula and Claude Code as default tools (not optional), proactively report progress and blockers, and contribute to technical documentation. Their usual channel is the India Tech Lead — they do not go directly to Chile Lead without prior agreement.
🚫 Does NOT do this
  • Asumir silenciosamente que entiende un ticket ambiguo — pregunta primero
  • Implementar sin leer el Intent Document del Bolt
  • Ignore a blocker for more than 2 hours without escalating to the TL
  • Close a ticket without tests and without technical documentation
  • Usar el stack o enfoque que le gusta sin consultar al TL
  • Skip the PR process due to time pressure
✅ DOES do this
  • Uses Nébula and Claude Code on every ticket — documents how in the PR
  • Posts the async stand-up every day at 9:30 AM IST without exception
  • Escribe PRs con contexto suficiente para que el TL haga un review real
  • Updates the Context Engine when closing a ticket with relevant technical decisions
  • Pregunta en el canal of the project, no en DMs — el contexto beneficia a todo the team
  • Completes the good-first-issue on Day 1 of onboarding without waiting for help
